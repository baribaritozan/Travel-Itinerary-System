# Phase 4 提案：旅行中のオフライン閲覧と地図・経路改善

検討日: 2026-10-12 JST。当初提案の履歴。実装の正本はSPECIFICATION.md v0.5 §23とdocs/PHASE4_PLAN.md。以下の背景地図保存/provider比較は後続の参考とする。

Phase 3は利用者確認後、明示承認を受けて [PR #2](https://github.com/baribaritozan/Travel-Itinerary-System/pull/2) をmainへmerge済み。merge commit: `561d9736e9f2d5250c308b76a4a9446675a43434`。本提案はその実装を基準とする。

## 1. 推奨範囲

利用者の回答により、初期のオフライン地図は「閲覧済み範囲を参照」とする。地域の事前一括ダウンロードは含めない。

| 区分 | 初期対応の提案 | 後続候補 |
| --- | --- | --- |
| 旅程 | 最後に正常取得した公開旅程を保存し、圏外での再読み込み・再起動後も閲覧 | 複数旅行の保存、オフライン編集 |
| 地図 | 保存旅程の地点・概略線、利用条件を満たす配信元の閲覧済み背景タイル | 地域ダウンロード、ベクトル地図への移行 |
| PWA | ホーム画面への追加、起動用ファイルの保存、更新通知 | Push通知、Background Sync |
| 移動表示 | 地図の移動線に交通手段のアイコンと名称を表示 | 実道路・鉄道形状、運行情報 |
| 経路 | 登録した出発地→到着地と、現在地→目的地を明確に分ける | 同一手段の複数経由地、任意Google Place ID |

旅程のオフライン対応は先行可能。背景地図の保存は配信元条件の確定が必要で、この点を満たすまで「背景地図もオフライン対応済み」とは扱わない。

## 2. 現行実装から見える差分

- `src/worker.mjs`のキャッシュはサーバー側Durable Object。端末が圏外なら到達できず、現在のブラウザ内には旅程保存処理がない。
- `public/index.html`と`public/app.js`はLeafletをunpkgから取得する。旅程だけを保存しても、圏外で新しく開いたときに地図ライブラリを取得できない。
- `public/app.js`はOSM標準ラスタタイルを使用。`Transit`の線は概略線であり、実際の道路・鉄道経路ではない。
- 交通手段はカード内に既に表示される。地図上の線・popupでは手段を識別しにくい。
- `public/model.mjs`のDirectionsは取得済みの現在地を出発点にする。旅程に登録済みの出発地から調べるだけでも位置取得が必要になる。
- 現在地はメモリ限定。オフライン保存を追加しても、この規則は維持する。

## 3. 仕様案：公開旅程のオフライン閲覧

### 3.1 保存と表示

1. 初期は既存の公開対象1旅行だけを扱う。正常な公開API payloadをアプリ側で検証して、旅行単位のsnapshotとしてIndexedDBへ保存する。新しい保存機能と端末保存中であることを画面に明示する。
2. 旅程名、日付、階層、地点の公開座標・住所、費用、営業時間、公開URLを保存する。表示から隠れている日付・候補・寄り道も含め、公開payload全体を保存する。
3. 起動時は有効なsnapshotがあれば直ちに表示し、並行して公開APIを取得する。初回ネットワーク待機の目安は3秒とし、保存旅程がある場合は通信完了を待たせない。
4. HTTP成功だけで保存せず、schema・旅行slug・公開ID・日時などを検査する。失敗・不正JSON・不適合schemaは直前の正常snapshotを上書きしない。
5. 成功時は旅行snapshotを原子的に置換する。削除・非公開化された項目は新snapshotから除去し、前後の配列を継ぎ足さない。遅れて届いた古い応答が新しい取得結果を上書きしないよう要求順と生成時刻を検査する。
6. 「Notion同期時刻」「端末保存時刻」「保存旅程を表示中」「通信確認中／失敗」を分ける。`X-Itinerary-Cache: stale`で返った内容を新鮮なNotion同期と表示せず、有効期限も延長しない。
7. 保存なしで圏外なら、空の旅程に見せず「保存済みの旅程がありません。通信できる場所で一度開いてください」と表示する。
8. オフライン中も日付切替、詳細、候補、系列、自由時間、寄り道、選択、フィルター、地図時間範囲を操作できる。比較用の選択状態などは従来どおり一時状態とする。
9. 再接続時は通常GETを1回再試行し、取得結果で接続状態を判断する。`navigator.onLine`だけを根拠に接続成功としない。再取得POSTの自動再送・キュー保存は追加せず、既存60秒制限を維持する。

snapshotの提案metadataは `schemaVersion / tripSlug / generatedAt / savedAt / expiresAt / sourceCacheStatus / payload`。Notionの内部IDや非公開情報を追加しない。HTTPの`Cache-Control: no-store`は維持し、意図した公開snapshot保存と通常のHTTPキャッシュを区別する。

### 3.2 保存期間・公開取り下げ

確定仕様（2026-10-12）は、明示的な端末保存から30×24時間有効、1旅行1最新版。同じ同期版の再取得では延長せず、新しい正常同期版で期限を更新する。期限切れpayloadを削除し、metadataで同版の自動復活を防ぐ。詳細はSPECIFICATION.md v0.5 §23とPHASE4_PLAN.mdを参照する。

公開後にNotionのPublishをfalseへ戻しても、圏外端末の保存内容を即時削除することはできない。正式仕様にはこの性質を明記し、再接続時の丸ごと置換・期限・「端末の保存データを削除」で扱う。オンラインで404/公開取り下げを確認した場合は、その旅行snapshotを破棄して表示を終了する。一時的な5xx/timeoutとは区別する。

保存容量不足や保存禁止の場合、オンライン表示は継続し「この端末には保存できませんでした」と通知する。ブラウザによる保存領域の削除も起こり得るため、「一度保存すれば必ず残る」とは保証しない。[保存容量と削除の仕組み](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

### 3.3 現在地・保存範囲

現在地の緯度経度・精度・取得時刻、現在地入りDirections URL、現在地markerを含む画面画像は保存しない。汎用のstate全体をJSON化せず、公開payloadだけを保存する。現在地由来の地図中心も復元用metadataへ保存しない。

キャッシュの許可対象は自前の起動用ファイル、公開snapshot、許可された背景タイルだけとする。Google Maps・予約先ページ・外部リンク・POST・webhookはキャッシュしない。閲覧済みタイルの座標番号は閲覧範囲を推測できる情報なので、地図範囲が端末に保存されることと削除手段も説明する。

保存無効化後はsnapshotと背景タイルを削除する。PWA起動用ファイルまで削除する操作は別にし、「保存旅程を削除」と「オフライン機能を無効化」の範囲を明示する。

## 4. 仕様案：PWAと閲覧済み地図

### 4.1 起動用ファイル

Service Workerは起動用ファイルと許可済み地図要求だけを担当し、旅程snapshotの検証・保存はアプリ側が担当する。役割を分けることで、APIのPOSTや現在地入りURLが汎用キャッシュへ紛れ込むことを防ぐ。

Leaflet JS/CSSと関連画像を既存依存から同一originへ配信し、ライセンスを同梱する。HTML/CSS/JS/manifest/iconをバージョン単位で保存する。依存ファイルにはビルド時の内容ハッシュを付け、読み込み途中で新旧コードが混ざらないようにする。Service Workerでの応答・キャッシュの基礎は [MDNのService Worker資料](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers) に従う。

manifestにはname/short_name/start_url/scope/id/display/theme_colorと192/512px・maskable iconを用意する。ブラウザで使う場合にもオフライン閲覧は提供し、インストールを必須にしない。インストール操作は対応ブラウザに合わせ、iOSではホーム画面追加の案内を用意する。[インストール要件とブラウザ差](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)

新Service Workerは必要ファイルの保存完了後に待機し、「更新があります」を表示する。利用者の操作後に切り替え、旅行中の画面を突然reloadしない。別タブの旧版が利用中なら旧版assetsを保持する。データschemaはコード版と分けて検証する。

### 4.2 背景タイルの利用条件

現行`tile.openstreetmap.org`のポリシーはオフライン利用・prefetchを禁止する一方、HTTP条件に従う通常のローカルキャッシュ再利用を認めている。通常キャッシュの存在を、アプリのオフライン地図機能を提供できる許可とは扱わない。初期範囲が「閲覧済み」でも、意図的なオフライン保存を許す配信元を選ぶ。[OSMF Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/)

| 選択肢 | 評価 | 判断 |
| --- | --- | --- |
| 現行OSM標準タイルをSWで保存 | 変更は小さいが、専用オフライン機能の利用条件を満たせない | 採用しない。通常オンライン表示だけは継続可能 |
| ブラウザ/PWAでの端末オフライン保存を許す配信サービス | Leafletを維持しやすい。契約・保存期限・料金・CORSの確認が必要 | 第一候補。対象用途への明示許諾を確認して選定 |
| 利用権のある地図データを自前配信 | キャッシュ方針を管理できる。配信費・データ更新・帰属表示を運用する必要 | 代替案。既存Workerに無断で新binding等は追加しない |

調査例ではStadia Mapsの資料にモバイルアプリ向けオフライン許可があるが、PWAにも同じ許可があるとは断定できない。MapTilerの通常ブラウザキャッシュの説明も、長期オフライン保存の許可を意味しない。採用サービスは未決定で、契約開始・課金・外部構成変更は本検討では実施しない。[Stadia利用条件](https://stadiamaps.com/terms-of-service/)、[MapTilerブラウザキャッシュ説明](https://docs.maptiler.com/guides/maps-apis/maps-platform/how-are-the-tile-requests-cached-in-web-browser/)

自前配信の候補にはラスタXYZやPMTilesがある。PMTilesは部分取得やXYZ配信に利用できるが、初期対応でMapLibre等への全面移行まで行う必要はない。元データ・スタイル・フォントの権利確認は別途必要。[Protomaps配信構成](https://docs.protomaps.com/deploy/)

### 4.3 保存・容量・欠損時の動作

配信元が確定した後、利用者が実際に表示したタイルだけを通常の画面要求から保存する。範囲・zoomの先読み、非表示画面の描画による取得、地域ダウンロードボタンは作らない。

- 背景タイルはcache-first、期限後は接続時に再検証。期限切れを圏外で返せるかも配信条件に従う。保存キーには配信元・地図版・style・z/x/yを含める。
- CORSで内容と成功statusを検査できる応答を採用し、読めないopaque応答は初版の永続保存対象外にする。許可host/path以外を保存しない。[Cache.putの応答制約](https://developer.mozilla.org/en-US/docs/Web/API/Cache/put)
- 仮の上限は背景50MiBか1000タイルの先に達した側。実端末検証と配信条件で確定し、最近使っていないタイルから削除する。起動用ファイルと旅程はタイルの整理に巻き込まない。
- 未保存の範囲・zoomへ移動したら、背景の欠損を薄い領域と説明文で示す。保存済みの地点名・pin・概略線は表示し、既存のfocus/選択操作も継続する。架空の道路や補完した地図を表示しない。
- 「背景は閲覧済み範囲のみ」「旅程保存済み／未保存」「保存日時」「保存量の目安」「削除」を確認できるようにする。地図全域を保存済みと表示しない。

## 5. 仕様案：地図・外部経路の改善

### 5.1 交通手段の地図表示

`Transit.transport`の既存値Walk/Train/Bus/Car/Ferryを使用し、同期schemaや既存Notion行の変更は初期対応に不要。線の中点に交通手段アイコン＋短い名称、popupに出発地→到着地・手段・予定時間を表示する。未設定は「移動手段未設定」とする。

色は既存のfocus/選択状態に使用し、交通手段を色だけで区別しない。短い区間・重複区間ではラベルを整理しても、focusした区間では手段を確認できるようにする。既存44pxの線hit領域、キーボード操作、候補・寄り道の明示表示条件を維持する。「概略線」の注記はラベル追加後も残す。

### 5.2 経路操作を二つに分ける

| 操作名の案 | 出発地と目的地 | 位置権限 |
| --- | --- | --- |
| Google Mapsで予定区間を開く | Transitの登録出発地→登録到着地 | 不要 |
| 現在地から到着地への経路 | 明示操作で取得した新鮮な現在地→登録到着地 | 必要。従来の5分判定を維持 |

通常Item・自由時間内候補は「現在地からこの場所へ」を維持する。Series/Alternative Groupは表示対象の子またはアクティブ候補から解決し、非表示の全候補を連結しない。自由時間の親そのものに目的地は割り当てない。

リンクの直前に出発地・到着地・手段を表示する。公開座標を優先し、なければ公開住所を使用。片側を解決できない予定区間リンクは無効化して不足を説明する。現在地がなくても予定区間リンクは使える。

URLは既存の固定HTTPS送信先・`api=1`・URLSearchParams・noopener/noreferrerを維持し、関数を「区間の解決」と「URL生成」に分ける。許可パラメーター以外は追加しない。Googleへの送信は明示操作時だけ行い、現在地入りURLは保存しない。

| 登録手段 | Google Mapsへの指定 | 表示上の扱い |
| --- | --- | --- |
| Walk | walking | 徒歩 |
| Train / Bus | transit | アプリ内では電車・バスを区別。Google側への固定指定は公共交通 |
| Car | driving | 車 |
| Ferry / 未設定 | travelmode省略 | 船専用の指定がないことを説明し、Google側で確認を案内 |

Google Maps URLには2048文字制限、経由地数・製品ごとの対応差がある。初版は1区間ごとのリンクを基本とし、混在手段のSeriesや船を一つのルートとして自動連結しない。ナビが必ず開始するとは表示しない。[Google Maps URLs公式仕様](https://developers.google.com/maps/documentation/urls/get-started)

寄り道には公開の`Rejoin Place`、未指定なら対象Transitの到着地を復帰地点として表示する。後続改善では「寄り道地点→復帰地点」を予定区間として開けるようにする。始点は明示した子Itemから解決し、Series/比較候補を勝手に採用済みと扱わない。

外部サービスのオフライン動作は本アプリでは保証せず、圏外時は接続が必要な場合があることを表示する。保存した地点名・住所を明示操作でコピーできるようにし、Clipboard失敗時は選択可能なテキストを残す。

| 段階 | 実施内容 | 主な変更箇所 | 完了条件 |

| 4B: 地図保存 | provider切替を設定化、閲覧タイル限定cache、期限・容量・欠損UI | 新map-cache/provider設定、SW、app/styles | 保存済み範囲を圏外で表示、未保存は明示 |
| 4C: 移動/経路 | 交通手段ラベル、予定区間リンク、解決結果preview、住所コピー | model/app/styles、単体・browser検証 | 位置取得なしで予定区間を外部へ渡せる |
| 4D: 本番検証 | 機内モード相当・再起動・復帰・PWA更新/rollback、実端末確認 | DEPLOYMENT、PHASE4_REPORT | 全受入基準と既存機能の回帰検証成功 |

4Cは4A/4Bに依存せず先行可能。利用者の旅行中の継続利用を優先する推奨順は4A→4B→4C。配信元の決定待ちが長ければ4A→4C→4Bとし、背景地図未完了を明記する。

Notion schemaは初期対応では変更不要。PlacesへのGoogle Place ID追加は後続候補とする。既存Worker/DOの更新制限・公開境界は維持し、自前地図配信を選ぶ場合だけ別途構成と運用を設計する。

## 8. 受入基準と検証案

| 基準 | 再現する検証 |
| --- | --- |
| A1 保存後の圏外再起動 | オンラインで保存→ページ/contextを閉じる→同じ永続profileで圏外起動。旅程、地点、概略線が表示される |
| A2 既存操作を維持 | 圏外で日付、詳細、候補、Series、自由時間、寄り道、選択、フィルター、地図時間を操作 |
| A3 新規端末の圏外初回 | 空profileで圏外にし、保存なしを説明。オンライン準備なしのオフライン起動は保証対象外 |
| A4 壊れた取得で正常保存を守る | timeout/5xx/不正JSON/不適合schema/遅れた応答。既存snapshotと同期時刻を誤更新しない |
| A5 公開変更を反映 | 再接続で項目減少・旅行404を返し、丸ごと置換または削除。古い公開行が残らない |
| A6 期限・容量・削除 | clockで期限超過、quota例外、ブラウザによる保存消滅、無効化を注入。オンライン表示は継続 |
| A7 閲覧済み地図だけ | 該当viewportを閲覧→圏外で再訪→未閲覧範囲/zoomへ移動。保存範囲のみ表示、欠損時もpin/線を操作 |
| A8 通信・保存境界 | 非表示タイルの取得なし、POST/外部URL保存なし、許可外host/opaque/失敗画像は保存しない |
| A9 現在地を保存しない | 固定位置取得→保存→全IDB/cache/metadata/ログ/要求を検査。reloadで現在地破棄、明示取得まで位置要求0 |
| A10 PWA更新と復旧 | 旧版の開いたタブ、新版途中失敗、利用者による更新、旧コードへrollback。新旧assetsの混在なし |

既存93単体・統合、35ブラウザの対象機能を維持し、新規テストを先に設計する。Phase 3のprivacy検証には「すべてのstorage/cacheが空」「SWなし」という広い期待値もあるため、v0.5に基づき「許可した公開データだけがある」「現在地・秘密値・許可外データがない」へ具体化する。現在地の非保存検証を削除するのではなく、保存された全構造の検査を追加する。期待値更新の根拠と差分は報告書へ記録する。

ブラウザ内のofflineフラグだけでなく、永続profile・実Service Worker・CDN遮断・ページ再起動を検証する。本番キャッシュとテストoriginのSWを混ぜない。地図の試験はローカルfixtureを使い、本番OSMへprefetchや自動走査を行わない。

## 9. デプロイ・復旧で追加すべき点

Service Workerはコードを旧版へ戻すだけでは消えない。配信中の`sw.js`更新、scope、HTTP cache制御、待機版の扱い、アプリ所有cacheのprefixを復旧手順へ含める。必要時は同じscopeでnetworkへ通す復旧用SWを配信し、利用中のタブと保存schemaの互換を検証する。一般の他アプリのcacheを一括削除しない。

既存Workerへのdeploy前に、新規インストールだけでなく旧版からの更新・旧版への復旧もstaging相当の独立originで検証する。新origin等の作成が必要なら実装計画で対象を確定する。本検討ではCloudflare/Notionへの追加変更、課金、次段階のデプロイは行っていない。

## 10. 実装前の残る判断

確定済みは「閲覧済み範囲だけを参照」。初回リリースは旅程PWAと経路改善で、背景タイル保存は後続とする。保存ボタンで有効化、30日、同版で延長なし、iPhone/Android実機確認は後続、本番デプロイ・報告・PR作成までが確定した。この提案の4Bとprovider比較は後続の参考資料であり、初回の必須範囲ではない。

最初の実装対象としては4Aを推奨する。地図配信元の選定と並行して、弱電波で旅程を開けなくなる現在の問題を解消できる。
